# Cashroom 심층 분석

기준일: 2026-11-08  
대상: 중학교 중심 교실경제 앱  
분석 상태: 공개 공식 홈페이지·Help·Pricing 기반. 실제 계정 실측은 미완료.

## 1. 왜 분석하는가

Cashroom의 독특한 점은 디지털화로 계산을 없애지 않고 오히려 ‘거래 순간’을 수학 학습으로 만든다는 것이다.

Class Money가 단순 장부 앱을 넘어 학습도구가 되려면 가장 깊게 참고할 사례다.

## 2. 제품 정체성

공식 문구의 핵심은 “Earn it. Save it. Do the math.”

학생은:
- 직업 지원
- 급여
- 청구서
- 상점
- 저축
- 이자
- 대출/신용
을 경험하고, 거래가 기록되기 전에 새 잔액을 직접 계산한다.

## 3. 핵심 인터랙션

예:
현재 Checking 41.25
Teacher Assistant 급여 +5
‘이제 잔액은 얼마인가?’
학생 입력
정답이면 기록

이 구조는 중요한 교육 설계 원리를 보여준다.

보통 핀테크 UX는 마찰을 줄이는 것이 목표지만 교육 앱은 일부 ‘생산적 마찰’을 의도적으로 남길 수 있다.

Class Money 적용:
Before → Change → Predict → Commit → Explain

단, 모든 학생에게 동일하게 강제하면 안 된다.

## 4. 개인별 학습 조정

Cashroom은 교사가 학생별로 Math Check를 끌 수 있다고 공개한다.

Class Money에서는 더 세분화:
- OFF: 자동 계산
- EASY: 두 선택지
- STANDARD: 직접 금액 입력
- GUIDED: 자리값/식 힌트
- ADVANCED: 식 또는 이유까지 기록

이 설정은 학생에게 공개적인 ‘난이도 꼬리표’로 보이면 안 된다.

## 5. 직업과 기본 참여소득

모든 학생은 자동으로 Student job을 가질 수 있고 교사가 금액을 정하거나 끌 수 있다. 추가 직업은 학생이 간단한 서술형 지원서를 작성한다.

이 구조는 Class Money에 적합하다:
- Student/기본 참여급여 = 경제 참여권
- 추가 Job = 책임·경험·추가소득

직업을 못 얻은 학생이 경제 시스템에서 탈락하지 않는다.

## 6. 자동화와 의미의 균형

공식 설명상 Payday와 Bills는 스케줄대로 자동 실행되며 로그인 중이 아니어도 작동한다.

좋은 자동화:
- 교사 반복업무를 제거한다.

하지만 학생에게는:
- 급여 명세
- 청구 내역
- 이전/이후 잔액
- 계산 확인
을 남긴다.

이것이 Class Money의 자동화 원칙이어야 한다.

‘백엔드는 자동, 학생의 이해는 자동화하지 않는다.’

## 7. 단일 요청함

Cashroom은 job applications, loan requests, store orders, below-zero alerts 등을 한 벨 영역에 모은다고 설명한다.

Class Money 적용:
교사 홈의 첫 화면을 통계가 아니라 Inbox/Today로 설계.

예:
- 상점 주문 5
- 과업 승인 7
- 직업 지원 3
- 실패한 급여 1
- 금요일 자동급여 예정 25

교사가 메뉴를 찾아다니지 않게 한다.

## 8. Undo 설계

Cashroom은 단순 거래는 History에서 undo하고, 구매·대출·경매처럼 연결 상태가 있는 것은 해당 기능에서 되돌린다.

이 구분은 매우 중요하다.

Class Money 내부 설계:
- 일반 지급: 역거래
- 상점: 주문 환불 상태 + 재고 복구 + 역거래
- 경매: 낙찰 상태 변경 + hold 해제
- 대출: 원금/이자 스케줄 정정

‘잔액 숫자만 원래대로’ 하면 안 된다.

## 9. 상점과 영수증

주문은 교사 승인 후 확정되고 영수증을 제공한다. 거절 시 돈과 쿠폰이 돌아오는 구조가 공식 Help에 설명된다.

Class Money:
- 요청 시 돈 hold
- 승인 시 settlement
- 거절/취소 시 release
- 영수증에는 상품, 가격, 날짜, 승인자, 구매 후 잔액

이 구조는 동시 구매와 과소비 문제를 방지한다.

## 10. 저축

학생은 checking에서 savings로 옮기고 목표를 설정하며 일정에 따라 이자를 받을 수 있다.

Class Money에서는 저축을 ‘숨겨진 잔액’이 아니라 목적이 있는 별도 공간으로 보여준다.

학생 홈:
- 사용 가능 80
- 저축 50
- 내 목표 ‘학급 상점 책갈피’ 50/100

## 11. 대출과 신용의 평가

Cashroom은 300~850 신용점수, 연체 영향, I=Prt 계산을 포함한다.

중학생 금융수업에는 의미가 있지만 한국 초등 Class Money MVP에서는 과도하다.

문제:
- 점수화된 신용도가 학생 정체성처럼 보일 위험
- 부채를 게임화할 가능성
- 1~4학년에는 개념 부담이 큼

따라서 P3 선택 시나리오로만 검토.

## 12. 배지

자동 배지는 첫 급여, 저축, 계산 정답, 대출 상환 등 경제활동의 이정표를 보상한다.

Class Money에서 좋은 게임화는:
‘랜덤 보상’보다 ‘배운 행동의 이정표’다.

예:
- 첫 저축 목표 설정
- 4주 예산 계획 유지
- 첫 공공예산 투표 참여
- 거래내역을 보고 오류 찾기

## 13. 개인정보 최소화

Cashroom은 시작 코드, first name + last initial 등 최소 정보를 설명한다.

Class Money도:
- 학생 이메일 필수화 금지
- 전체 실명 대신 학교 정책에 맞게 번호/별칭 허용
- 학급 외 조회 차단
- 공유기기 세션 종료 명확화

## 14. Class Money에 가져올 것

가장 강하게:
1. 거래 전 예상 잔액
2. 학생별 계산 모드
3. 기본 Student income + 추가 직업
4. 자동급여/자동청구
5. 단일 교사 Inbox
6. 연결 거래의 기능별 Undo
7. 영수증
8. 경제 이정표형 배지

보류:
- 신용점수
- 대출
- 경매
- 쿠폰

## 15. Craft Anything 후속 실측

- 학생 거래 계산 오답 시 피드백
- 연속 오답 처리
- 계산모드 OFF 학생의 UI 차이
- 급여가 자동 생성된 후 학생이 ‘record’하기 전 상태
- 상점 주문의 돈 hold 시점
- 주문 거절 후 환불 표시
- History에서 undo 가능한 범위
- 알림 벨 우선순위
- 학생 25명에서 교사 홈 밀도
- 폰/태블릿 UI

## 16. 현재 판단

Cashroom의 가장 중요한 가치는 많은 금융기능이 아니다.

‘거래를 학생에게 의미 있는 사고 순간으로 남긴다’는 설계가 핵심이다.

Class Money가 경쟁서비스와 차별화하려면 이 원리를 더 초등 친화적으로 일반화하는 것이 효과적이다.

## 심화 보완: 12개 분석축

### A. 사용자와 권한
Cashroom은 교사와 학생을 명확히 분리하고 학생 이메일 없이 username/student ID 중심 접근을 제공한다. 교사는 자동급여·청구·상점·대출 등 규칙을 설정하고 학생은 자신의 거래를 처리한다.

Class Money는 이보다 더 세밀하게:
- 교사 설정권한
- 교사 거래권한
- 학생 본인 지갑
- 학생 보조역할
을 분리하는 것이 좋다.

### B. 거래 상태전이
Cashroom의 핵심은 거래가 생긴 뒤 학생이 새 잔액을 계산해 Record하는 단계가 있다는 것이다.

거래예정 → 학생 계산 → 정답확인 → 기록완료

Class Money에서는 금융원장과 학습단계를 분리할지 결정해야 한다.
권고는 돈 자체는 서버에서 원자적으로 반영하고, 학생에게 별도의 확인/계산 activity를 남기는 방식이다. 그래야 학생이 앱에 늦게 접속해도 실제 경제상태가 모호해지지 않는다.

### C. 교사 JTBD
교사가 원하는 주요 업무는:
- 자동급여 일정 설정
- 청구일 설정
- 한 곳에서 승인요청 확인
- 잘못 지급한 돈 즉시 복구
- 학생별 계산면제
- 거래내역 export

Class Money는 이를 '오늘의 운영' 카드로 묶는 것이 적합하다.

### D. 학생 JTBD
- 직업지원
- 급여확인
- 청구서 납부 결과 이해
- 상점 구매
- 저축목표
- 필요시 대출개념 학습

모든 행동에서 학생에게 이전잔액, 변화액, 이후잔액을 보여주는 것이 핵심 패턴이다.

### E. 자동화
Payday와 bills는 로그인 없이 예약 실행된다고 설명한다. Class Money가 같은 수준의 자동화를 구현하려면:
- scheduler
- idempotency
- execution log
- retry policy
- class paused 상태
- term end
가 필요하다.

자동화는 편의기능이 아니라 회계정합성 기능이다.

### F. 승인 Inbox
Cashroom의 alert bell은 여러 기능의 대기사항을 한곳에 모은다.

Class Money 승인함의 권고 분류:
- 상점 주문
- 직업 지원
- 고액 특별거래
- 학생간 거래
- 오류/음수위험
- 대출 신청

'메뉴별 대기건수'보다 '오늘 결정을 요구하는 일' 중심이어야 한다.

### G. 경제학습
Cashroom은 계산, 이자, 신용, 대출을 수학과 연결한다. 장점은 실제 계산 맥락이 있다는 것이고 위험은 금융학습보다 계산문제가 전면에 나올 수 있다는 것이다.

Class Money는 계산 외에도:
- 선택 이유
- 기회비용
- 다음 계획
을 포함해야 한다.

### H. 상점·쿠폰·경매의 데이터 모델
필요 객체:
- order
- coupon
- bid
- auction
- inventory hold
- refund

경매는 최고입찰자의 자금을 임시 예약하지 않으면 학생이 여러 경매에 가진 돈보다 많이 입찰하는 문제가 생긴다.

### I. 신용과 대출 위험
신용점수는 실제 금융을 잘 모사하지만 교실에서는 학생의 인성이나 신뢰도 점수처럼 오해될 수 있다.

Class Money는 대출 모듈을 도입한다면 공개점수를 제거하고:
- 상환일
- 남은 원금
- 이자
- 납부기록
만 개인에게 보여주는 편이 안전하다.

### J. 실패모드
- 자동급여 중복
- bill과 구매가 동시에 실행되어 음수
- 주문 거절 환불누락
- 쿠폰 복원누락
- undo가 이자/신용 계산을 되돌리지 못함
- loan 상환 중 수업종료
- 학생 계산미완료가 장기간 누적

Class Money 테스트에서 기능별 Undo의 연쇄효과를 반드시 확인해야 한다.

### K. 제품결정
Adopt:
- 통합 Inbox
- 자동급여
- 학생별 계산설정
- history/undo
- savings goal
- 이메일 없는 학생계정

Adapt:
- bills
- auctions
- coupons
- loans

Avoid initially:
- 공개 credit score
- 부채를 핵심 게임루프로 만드는 구조

### L. 남은 실측
- 거래를 학생이 Record하기 전 교사/학생 잔액
- 계산 오답 피드백
- 자동급여 실패 표시
- 상점 자금 차감 시점
- refund 시 쿠폰 복원
- undo의 연쇄범위
- 모바일 정보밀도
