# 사용자 여정·화면 설계·예외 시나리오

상태: 가설 및 테스트용 스토리보드 (실제 앱 화면 아님).

## A. 교사: 빠른 시작
| 단계 | 화면/행동 | 성공 조건 | 실패/복구 |
|---|---|---|---|
| 1 | 반 만들기: 이름/학년/화폐명 | 1분 내 학급 초안 | 필수항목 명확히 안내 |
| 2 | 학생 번호·별칭 25명 붙여넣기 | 미리보기→일괄 등록 | 중복 번호/빈행 수정 |
| 3 | 직업/급여 추천값 선택 또는 생략 | 최소 1개 보상 방식 활성 | 조건 없이 다음 가능 |
| 4 | 상점 상품 3개 등록 또는 생략 | 가격·재고 확인 | 구매 불가 상품 표시 |
| 5 | 첫 일괄 지급 | 수혜자 목록·금액·합계 미리보기 | 취소/실패 학생 재시도 |
| 6 | 학생 접근 설정 | 학생 로그인 선택/교사 단독 운영 | 유출된 코드 폐기/재발급 |

## B. 교사: 수업 중 5초 내 보상 흐름 (목표값, 미측정)
열려 있는 지급 패널 → 학생 선택 → 금액/사유 템플릿 → 지급 완료 확인. 개인/모둠/전체 동일 인터랙션 사용. 결과 화면에서 실제 원장 기록 재조회. 여기서 '5초'는 테스트 목표지 실측 결과가 아님.

## C. 학생: 첫 경제 활동
1. 내 잔액/최근 내역 확인: 계좌 명칭과 화폐단위 이해.
2. 내 직업에 해당하는 일이 무엇인지 확인하고 수행 여부 표시(설정한 반만).
3. 급여가 지급되면 '왜 이 금액을 받았는가'를 영수증처럼 표시.
4. 상점에서 상품 선택 → 구매 후 예상 잔액 확인 → 구매 요청/확정.
5. 저축 목표가 있다면 '지금 사기 vs 목표를 위해 모으기' 비교.
6. 주간 회고: 내가 한 선택, 대안 선택의 결과, 다음번 계획.

## D. 교사 승인함
한 화면에서 대기요청을 유형별로 보고 승인/거절. **취소가 가능한 요청과 거래가 이미 확정된 경우를 분리**한다.
- 직업 신청: 신청→대기→배정/반려.
- 상점 주문: 대기→승인/거절→영수증. 승인 시 잔액/재고 재검증.
- 특별 지급: 교사 직접 수행 또는 검토형.
- 부분 실패, 중복 클릭, 인터넷 단절 등 명시적 상태 표시.

## E. 예외 플로우
| 상황 | 제품 반응 |
|---|---|
| 상품 가격이 요청 후 바뀜 | 주문의 가격 스냅샷 유지 또는 가격 변경 재동의(정책 결정 필요) |
| 결제 직전에 다른 구매 발생 | 최신 잔액으로 검증하고 부족하면 실패 안내 |
| 급여 실행 중 재시도/새로고침 | 같은 지급기간에 중복 지급 방지 |
| 교사가 학생을 잘못 선택해 지급 | 원거래 참조 정정·복구 이력 표시 |
| 학생이 다른 계정으로 로그인 | 자신의 학생 ID 외에는 API 접근 불가 |
| 공유 태블릿에 학생 세션이 남음 | 로그아웃 쉽게 제공, 자동 만료 |
| 기기가 오프라인 | 거래 성공으로 표시하지 않고 재연결/재확인 안내 |
| 재고가 마지막 한 개 남음 | 최초 성공한 승인만 확정, 나머지 실패 |
| 학생이 탈퇴/반 이동 | 거래 기록의 정합성 유지하면서 개인정보 보존정책 준수 |

## F. 교실 운영 도구의 화면 원칙
- 교사 홈은 통계보다 **오늘 처리할 업무**를 먼저 표시.
- 학생 홈은 게임 메뉴보다 **잔액·최근 변화·오늘 할 일**을 먼저 표시.
- '돈 받기'/'돈 쓰기'/'저축하기'를 명확히 분리; 항상 이전/이후 금액 표시.
- 고액/전체 대상 지급은 완료 전에 대상 인원과 합계를 재확인.
- 과거 지급의 정정은 단순 '삭제'가 아니라 정정 이유 입력.
- 상점은 실물·권리/특혜·공동체 경험 유형을 구분; 제한 상품 자동 검토.
